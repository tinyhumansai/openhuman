# 施工合同纠纷全流程分析

## 概述

本 Skill 覆盖建设工程施工合同纠纷处理的完整流程：从合同条款摘录研判、工程款利息核算、证据组织，到争议焦点分析、索赔抗辩、诉讼执行和标准化成果输出。

**核心原则**：本 Skill 编排已有 Skill（pdf/docx/xlsx/proma-cloud-sdk），不重复造轮子。

## 核心分析规则

### 规则一：条款分析必须摘录原文

进行任何条款分析时，必须先引用合同**原文**（从提取的合同文本中截取），再进行分析。不得仅用概括性语言描述条款内容。

输出格式强制要求：
```
**原文摘录**：
> [从合同中直接引用的条款原文，保留原文表述]

**分析**：
[基于原文的风险识别、裁判影响、争议研判]
```

没有原文引用的条款分析视为不完整，必须补充。

### 规则二：全部任务完成后进行扫描检查

所有分析模块完成后，必须执行最终扫描检查：

1. **完整性检查**：23 类条款（C1-C23）是否全部覆盖？有无遗漏的关键条款类型？
2. **一致性检查**：各模块的结论是否互相矛盾？数据是否一致？
3. **原文对照检查**：关键结论是否有原文支撑？摘录内容是否准确？
4. **风险遗漏检查**：是否存在明显的未覆盖风险点？
5. **输出格式检查**：Excel 是否所有 Sheet 完整？表格是否有断行或乱码？

扫描检查完成后输出检查报告：

```markdown
## 最终扫描检查报告
| 检查项 | 状态 | 说明 |
|--------|------|------|
| 条款覆盖 | 13/13 | 全部覆盖 |
| 原文支撑 | OK | 关键结论均有原文引用 |
| 数据一致 | OK | 各模块数据一致 |
| 风险遗漏 | 0 | 未发现遗漏 |
| 输出格式 | OK | Excel 3 Sheet 完整 |
```

### 规则三：来源溯源标签

所有法律引用和事实陈述必须标注来源类型。标签体系详见 `references/risk-methodology.md` 第一章：

| 标签 | 适用场景 |
|------|---------|
| `[法条原文]` | 直接引用法律法规条文原文 |
| `[司法解释]` | 最高法司法解释或批复 |
| `[裁判规则]` | 裁判文书提炼的司法实践共识 |
| `[合同原文]` | 摘录自用户上传的合同文件 |
| `[已核实]` | 当前会话中已通过检索工具独立核实 |
| `[需验证]` | 来源于模型训练数据，未独立检索核实 |

**铁律**：每条法律主张必须附带至少一个来源标签。关键法条必须同时标注内容标签 + 验证标签。未连接检索工具时，所有引用统一标注 `[需验证]`，不得省略。

### 规则四：严格模式护栏

本 Skill 运行在**严格模式**下，遵循以下护栏规则（详见 `references/risk-methodology.md`）：

1. **禁止静默补充（三值选择）**：信息不足时必须在 `是` / `否` / `需确认` 中做出选择。不得在 `[需确认]` 状态下给出确定性结论。必须明确标注假设前提。
2. **时效触发检查**：遇到价款争议/质量缺陷/欠款/索赔/裁决执行时，主动检查相关时效是否届满。
3. **用户陈述核实**：用户提供的履约事实标注 `[用户陈述]`，在证据组织中提示需要对应证据支撑。
4. **目的地检查**：输出前验证结论在"律师审查草稿"定位内，含免责声明，来源标签完整。
5. **跨模块严重性下限**：任一模块评估为"严重"的风险在最终报告中保留"严重"级别，不得因其他模块低评估而降低。

## 案件复杂度评估与架构模式选择

根据案件特征自动选择最适配的处理模式：

| 案件特征 | 推荐模式 | 说明 |
|---------|---------|------|
| 单合同 + 单争议焦点 + 无鉴定 | **Pipeline** | 标准顺序流程 |
| 需要法律研究/类案检索 | **内嵌 Fan-out/Fan-in** | 在争议研判阶段并行调用 construction-legal-research |
| 涉及造价/工期/质量鉴定 | **内嵌 Expert Pool** | 在争议研判阶段按需调取 construction-expert-evaluation |
| 需要起草法律文书 | **内嵌 Producer-Reviewer** | 输出阶段调用 construction-legal-writing |
| 复杂案件（多争议点+鉴定+文书） | **Supervisor** | 先 WBS 拆解，再调度各子任务 |
| 大型纠纷（多方主体+多个案由） | **Hierarchical Delegation** | 策略层→组长层→执行层三层分级 |

### 快速判断

```
案件进入 → 评估复杂程度
  ├── 简单（单个问题）→ 直接查模块决策树，单模块处理
  ├── 标准（全流程分析）→ Pipeline 模式
  ├── 复杂（多争议点/需鉴定/需文书）→ Supervisor 模式
  └── 大型（多方多案由/集团诉讼）→ Hierarchical Delegation 模式
```

### Supervisor 模式执行逻辑

```
1. WBS 工作分解 → 将案件分解为独立工作包，标记前置依赖
2. 并行/串行调度 → 无依赖的并行，有依赖的按 Pipeline 串行
3. 结果汇总 → 跨模块一致性检查，整合为最终报告
```

### Hierarchical Delegation 模式执行逻辑

```
策略层（总负责人）：制定诉讼策略 → 分解为合同/证据/鉴定等组
  ↓
组长层：合同组/证据组/鉴定组各自管理子任务
  ↓
执行层：各子任务调用对应模块/Skill 执行
```

架构模式的完整设计说明见工作区级 `.context/construction-contract-architecture.md`。

## 集成方式

### 基础 Skill

- **pdf Skill**：用于 PDF 合并/拆分/文本提取。调用其 pdfplumber/pdftotext 模式
- **docx Skill**：用于最终报告生成。提供分析结果 JSON，委托其 docx-js 管线
- **xlsx Skill**：用于台账生成。提供计算数据，委托其 openpyxl 管线
- **proma-cloud-sdk**：用于批量 LLM 调用（逐条分析条款、分类证据等）

### OCR 文档处理管线

- **MinerU API**（云端）：扫描型 PDF 解析引擎，直出 Markdown，保留排版/表格/多栏。通过 `classify_and_extract.py` 自动调用。
- **`scripts/classify_and_extract.py`**：自动分类 PDF + 提取/MD 输出。文字型→pdfplumber（零资源消耗）；扫描型→MinerU 云端 API（PDF 直出 MD，不占本地算力）。
  - 安装: `pip3 install pdfplumber requests`
  - 用法: `python3 scripts/classify_and_extract.py input.pdf -o output.md`
  - 环境变量: `MINERU_API_KEY`（扫描型 PDF 需要）

### 流程支撑 Skill（工作区新增）

- **requirement-grill**：需求压力测试。用户需求模糊时启动结构化提问，精确化模糊术语，输出需求确认书。作为全量分析的强制前置步骤（P0），在首次案件接入时自动触发。
- **case-handoff**：案件上下文交接。阶段性分析完成后，将案件进度、关键发现、待办事项打包为 handoff 文档。在全部步骤完成或用户要求中断时自动触发。
- **construction-legal-research**：法律检索与类案分析。当需要法条/司法解释/案例/裁判口径检索时，委托其执行 Fan-out 并行检索 + Fan-in 综合整合。在争议研判阶段（模块4）或法律研究需求时内嵌调用。
- **construction-expert-evaluation**：专业鉴定评估。当涉及造价/工期/质量/司法鉴定程序时，委托其调取 Expert Pool 中对应专家模块。在争议研判阶段（模块4）或用户提到鉴定需求时内嵌调用。
- **construction-legal-writing**：法律文书起草审核。当需要起草起诉状/答辩状/代理词等文书时，委托其执行 Producer-Reviewer 双阶段流程。在成果输出阶段（模块8）或用户提到起草需求时内嵌调用。

### 子 Skill 调用规范

1. **数据传递**：调用子 Skill 前，先准备好案件上下文摘要（合同条款分析结果、核算数据、争议焦点等），作为子 Skill 的输入
2. **结果整合**：子 Skill 产出结果后，回收结果摘要到主案件上下文中，保持全案信息完整
3. **职责边界**：子 Skill 专注于自身领域，不重复执行主 Skill 已完成的合同分析和核算工作
4. **来源标签统一**：所有子 Skill 的分析结论沿用主 Skill 的[法条原文][司法解释][裁判规则][需验证]标签体系

## 风险方法论与安全护栏

本 Skill 融合 claude-for-legal-ZH 的风险方法论，详见 `references/risk-methodology.md`：

### 六维风险评价

每个条款和争议点从六个维度系统评估：**风险定性**（权利丧失/义务加重/责任豁免/程序障碍/证据困难/财务敞口）、**敞口规模**、**发生概率**、**可规避性**、**商业权衡**、**紧迫性**。

### 双轴严重性标尺

| 本文档用语 | 含义 |
|-----------|------|
| 监控 | 风险存在但不影响当前决策，定期复查 |
| 常规 | 施工合同常见风险，按标准流程处理 |
| 优先 | 需重点关注并在合理期限内采取措施 |
| 严重 | 必须立即处理，可能对案件走向有决定性影响 |

风险校准矩阵：法律风险 × 商业影响 → 监控/常规/优先/严重

### 内容分离纪律（五组分离）

诉讼材料准备中，以下内容必须严格分离：证据列举 / 质证意见 / 证据认定 / 查明事实 / 争议焦点。不得混合编排。

### 决策树

关键决策节点显式化：合同效力判断（资质→招标→转包→审批）、利息起算（约定→交付→结算→起诉）。模棱两可时列出多种解释并标注依据。

## 律师审查草稿声明

本 Skill 所有输出均为**律师审查草稿——不是法律意见**。每条结论：
1. 标注法域假设和来源标签
2. 主观法律判断优先标记 `[需审查]` 或 `[需确认]`
3. 任何提交/发送/依赖前必须经执业律师独立审查确认

## 批量分析策略

当用户需要全流程分析时，先评估案件复杂度，选择对应架构模式：

### 标准流程（Pipeline 模式）

0. **需求确认（Grill）** → 结构化提问确认角色/合同/诉求/材料，输出需求确认书（信息充分时跳过）
1. **案件复杂度评估** → 判断属于简单/标准/复杂/大型
2. **文本提取** → 通过 `classify_and_extract.py` 自动分类 PDF 类型。文字型→pdfplumber 直读（零资源消耗）；扫描型→MinerU 云端 API（PDF 直出 MD，不占本地算力）
3. **加载 risk-methodology.md** → 统一风险评价标准
4. **加载 module-1** → 条款摘录（产出：条款清单 + 六维风险矩阵）
5. **加载 module-2** → 如有付款记录则核算（产出：利息台账）
6. **加载后续模块** → 按用户需求加载（证据/争议/索赔/结算/程序/输出）
7. **最终扫描检查** → 完整性/一致性/原文对照/风险遗漏/格式检查
8. **Handoff 交接存档** → 打包案件上下文到工作区 `.context/handoffs/`

### 复杂案件流程（Supervisor 模式）

当案件涉及多争议焦点+鉴定+文书时，自动切换到 Supervisor 编排：

1. **WBS 分解** → 合同审查 | 款项核算 | 证据组织 | 法律检索 | 鉴定评估 | 文书起草
2. **并行执行无依赖任务** → 如法律检索和鉴定评估可同时进行
3. **串行执行有依赖任务** → 合同审查 → 争议研判 → 文书起草
4. **汇总与一致性检查** → 跨模块数据校验，整合报告

### 通用规则

- 首次分析建议先执行需求确认（Grill），信息充分时可直接从步骤 1 开始
- 用户需求模糊时**必须**先执行需求确认，不得在角色/合同/诉求不明确的情况下开始分析
- 每个模块分析完成后，将结果摘要保存到对话上下文，释放参考文件以节省 token
- 调用子 Skill 后回收其结果摘要，保持全案上下文完整
- 最终输出前执行最终扫描检查
- 全部步骤完成后必须执行 Handoff 交接存档，保存案件上下文到工作区 `.context/handoffs/`
- 用户要求中断时（"明天继续"、"先到这里"等）也应执行 Handoff，确保持续性
